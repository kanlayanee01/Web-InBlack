# ADR-0005: คิวงานบน PostgreSQL (เรื่องที่ยากที่สุด)

**สถานะ:** ใช้งาน

## ปัญหา

เรื่องที่ยากที่สุดของระบบนี้คือช่องว่างระหว่าง "บันทึกว่าจ่ายแล้ว" กับ "สั่งให้เติมเกม" ถ้า commit ลง PostgreSQL แล้วค่อย push งานเข้า Redis และ process ตายตรงกลาง ลูกค้าจะจ่ายเงินแล้วไม่ได้ของ และไม่มีใครรู้ ซึ่งคือการ "เสียเงิน" ตามโจทย์พอดี

## ทางเลือก

| ทางเลือก | ปัญหา |
|---|---|
| Redis queue | เกิดช่องว่างข้างต้น และ Redis ที่ถูก kill อาจทำงานหายถ้า fsync ยังไม่ทัน |
| Outbox + publisher ไป Redis | แก้ได้ แต่ต้องมี component เพิ่มและยังต้องกันซ้ำฝั่งผู้รับ |
| **ตาราง `jobs` ใน PostgreSQL** | throughput ต่ำกว่า Redis |

## การตัดสินใจ

ตาราง `jobs` อยู่ใน transaction เดียวกับการเปลี่ยนสถานะ ออเดอร์จึงเป็น `IN_QUEUE` โดยไม่มีงานไม่ได้

- รับงานด้วย `FOR UPDATE SKIP LOCKED` worker หลายตัวจึงไม่แย่งงานเดียวกัน
- Lease 15 วินาที ต่ออายุทุก 5 วินาที worker ตายแล้วงานกลับเข้าคิวเอง
- Retry แบบ exponential backoff พร้อม jitter
- `status = 'dead'` คือ dead-letter queue ซึ่ง query และแก้ไขด้วย SQL ได้ทันที

งบเวลาของการ retry ถูกคำนวณให้จบใน 2 นาทีตามข้อ 7 คือ 6 รอบ หน่วงรวมไม่เกิน 31 วินาที บวก timeout ต่อรอบ ออเดอร์จึงจบที่ `COMPLETED`, `FAILED` หรือ `NEEDS_REVIEW` เสมอ

โจทย์ระบุ Redis สำหรับคิวแบบ "หรือทางเลือกที่อธิบายได้" Redis ยังใช้กับ rate limit ซึ่งเป็นงานที่เหมาะกว่า เพราะข้อมูลหายได้โดยไม่เสียเงิน

## ผลลัพธ์

`docker kill` worker และ PostgreSQL ระหว่างทำงาน ทุกออเดอร์จบครบ ไม่มีงานหาย

ข้อแลกเปลี่ยนคือ throughput ของคิวบนฐานข้อมูลต่ำกว่า message broker เฉพาะทาง ผมยังไม่ได้วัดเพดานของคิวนี้ ถ้าปริมาณงานโตจนเป็นคอขวดค่อยเพิ่ม outbox ไปยัง message broker
