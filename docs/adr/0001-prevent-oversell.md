# ADR-0001: กันการ oversell

**สถานะ:** ใช้งาน

## ปัญหา

`FLASH-SKIN-01` มี 100 ชิ้น แต่อาจมีคนกดซื้อพร้อมกันหลักพันคนผ่าน API 2 ตัว ถ้าอ่านค่าก่อนแล้วค่อยเขียน สอง request จะเห็น stock เหลือ 1 พร้อมกันแล้วขายทั้งคู่

## ทางเลือก

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| Lock ใน Redis | เร็ว | ถ้า Redis ล่มหรือ lock หมดอายุกลางทาง จะ oversell ได้ และต้องดูแลสองที่ |
| `SELECT ... FOR UPDATE` แล้วค่อยลด | เข้าใจง่าย | เพิ่มรอบคุยกับ DB ถือ lock นานกว่า |
| **`UPDATE` แบบมีเงื่อนไข** | เช็กกับตัดเป็นคำสั่งเดียว | ต้องวางลำดับ lock ให้ดี |

## การตัดสินใจ

```sql
UPDATE products SET stock_remaining = stock_remaining - $2
WHERE id = $1 AND stock_remaining >= $2
RETURNING id
```

ถ้าไม่มีแถวกลับมาแปลว่าของไม่พอ แล้ว rollback ทั้งออเดอร์ โควตาต่ออีเมลและเพดานของโค้ดส่วนลดใช้วิธีเดียวกัน

ลำดับ lock คงที่ทุกเส้นทาง คือโควตาอีเมล, โค้ดส่วนลด, แล้วจึง stock โดยเรียงสินค้าตาม id ซึ่งกัน deadlock และ stock ที่แย่งกันหนักสุดอยู่ท้ายจึงถูกถือสั้นที่สุด

`CHECK (stock_remaining >= 0)` เป็นด่านสุดท้าย ถ้าโค้ดมีบั๊กก็ยังขายเกินไม่ได้

## ผลลัพธ์

ทดสอบยิงพร้อมกัน 1,500 request ผ่าน proxy จริงซ้ำหลายรอบ ขายได้ 100 ชิ้นพอดีทุกรอบ และไม่พบ deadlock ใน log

ของที่เติมให้ลูกค้าไปแล้วจะไม่คืนกลับเข้า stock แม้ถูก refund เพราะจำนวนที่ส่งมอบจริงจะเกิน 100 ได้ แต่โควตาต่ออีเมลจะคืนตามข้อ 4 ของโจทย์
