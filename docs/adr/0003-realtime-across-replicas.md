# ADR-0003: Real-time ข้าม replica

**สถานะ:** ใช้งาน

## ปัญหา

ลูกค้าอาจต่อ SSE อยู่ที่ `api-1` แต่ webhook เข้าที่ `api-2` หรือสถานะถูกเปลี่ยนโดย worker ต้องเห็นภายใน 2 วินาที และถ้าเน็ตหลุดต้องได้ event ที่พลาดครบ ไม่ซ้ำไม่ข้าม

## ทางเลือก

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| Redis pub/sub หลัง commit | ใช้กันแพร่หลาย | ถ้า process ตายหลัง commit ก่อน publish สัญญาณหาย และ Redis ล่มแล้วหยุด |
| Redis Streams + outbox | ทนทาน | ต้องมี publisher เพิ่มอีกตัว เกินจำเป็น |
| **PostgreSQL `LISTEN/NOTIFY`** | ส่งตอน commit พอดี | ถ้า connection หลุดจะพลาดสัญญาณช่วงนั้น |

โจทย์กำหนดให้ใช้ Redis หรือเทียบเท่าโดยต้องอธิบายถ้าเลือกอย่างอื่น นี่คือเหตุผล

## การตัดสินใจ

Trigger บน `order_events` เรียก `pg_notify` แต่ละ API replica มี listener 1 connection แล้วปลุกสตรีมของออเดอร์นั้น

NOTIFY ถูกส่งเมื่อ transaction commit เท่านั้น จึงไม่มีทั้งสัญญาณของงานที่ rollback และช่องว่างระหว่าง commit กับ publish

**สัญญาณเป็นแค่การปลุก ข้อมูลอ่านจาก `order_events` เสมอ** และแต่ละสตรีมอ่านซ้ำทุก 1 วินาทีเป็นตาข่ายรองรับ สัญญาณที่หายจึงทำให้ช้าลงได้ไม่เกิน 1 วินาที และไม่ทำให้ข้อมูลหาย

`seq` เป็นเลขต่อออเดอร์แบบไม่มีช่องว่าง เพราะเพิ่มภายใต้ lock ของแถวออเดอร์ `Last-Event-ID` จึงเล่นต่อได้ตรงทุก event ซึ่งการใช้ identity รวมทั้งตารางทำไม่ได้ เพราะลำดับการ commit อาจสลับกับลำดับเลข

## ผลลัพธ์

ทดสอบให้สตรีมอยู่ `api-1` และยิง webhook เข้า `api-2` เห็นสถานะภายใน 2 วินาที และสตรีมที่เปิดค้างยังได้สถานะครบหลัง restart PostgreSQL

ข้อแลกเปลี่ยนคือการอ่านซ้ำทุกวินาทีเพิ่มภาระตามจำนวนสตรีม ถ้าต้องรับจำนวนมากควรปรับเป็นอ่านแบบ batch ต่อ replica
